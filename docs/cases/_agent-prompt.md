# AI Agent 社区案例投稿提示词

> 使用方式：把本文件全文复制给能读取项目文件、编辑文件并运行命令的 AI Agent。适用于 Vibecoding（氛围编程，即用自然语言描述需求，让 AI 帮忙生成或修改代码）制作的界面，也适用于其他自定义界面。

## 可直接复制给 Agent 的提示词

你现在负责协助我为 Andrsion/lifeup-custom-frontend 准备一份社区界面投稿。你的任务是整理投稿材料、检查风险并生成草稿，不是替维护者审核或自动收录。

### 1. 先读取规则
如果当前工作区里有这个仓库，先读取：
- docs/cases/README.md（正式投稿规范）
- CONTRIBUTING.md
- LICENSE
- scripts/case_check.py 的使用方式；必要时查看其实现
- docs/cases/ 中的现有案例，了解格式（跳过以 _ 开头的辅助文件和目录）

如果当前工作区不是该仓库，先确认我提供的项目文件和仓库规范是否齐全。无法读取正式规范时，明确说明，不要臆造仓库要求；请提示我提供规范文件或打开仓库工作区。

### 2. 盘点项目并确认投稿类型
先检查当前项目文件，判断内容属于哪一种：
- 可运行界面（HTML / 示例项目）
- 主题或换名方案（不需要提交代码）
- 完整施工稿（界面规格与提示词）

优先利用现有内容，不要为了投稿重写整个项目。缺少必要信息时，只询问真正阻塞投稿的问题；不要猜测作者名称、灵感来源、授权意愿或数据来源。

### 3. 脱敏与安全检查
绝不把真实 Token、API Key、密码、个人数据、手机号、真实设备 IP、私有配置或备份写入投稿材料。
- 检查源码和将要提交的文件；特别留意 token、Authorization、内网 IP、手机号、邮箱、个人数据、config.json、.lfbak、备份文件，以及大段 base64。
- 不要为了通过检查而把真实敏感值复制到报告、终端输出或新文件中。发现疑似敏感内容时，报告文件名和大致位置即可，避免复述秘密值。
- 如果存在 scripts/case_check.py，按 docs/cases/README.md 中的方式实际运行它。若它报告 RED，先说明风险并修复投稿副本中的问题；未经我同意，不要擅自改动原项目的业务代码或删除原始文件。
- YELLOW / ⚠ 项必须逐项解释并确认是否需要修改，不能把“需修改后提交”说成“可提交”。
- 检查器不是完整的安全审计；即使通过，也要人工检查配置、日志、截图和文档是否泄露信息。

### 4. 生成投稿草稿
如果是可运行界面且仓库检查脚本可用：
1. 按正式文档的命令对目标 HTML 或目录运行 scripts/case_check.py。
2. 使用检查器支持的 --emit 与 --slug 生成草稿骨架。slug 使用简短的小写英文、数字和连字符。
3. 在生成的草稿中补齐实际可确认的信息；保留无法确认的项目为明确的“待作者确认”，不要编造。
4. 按规范说明数据来源：真实云人升数据、静态假数据或纯设计稿。默认优先用静态假数据或纯设计稿，除非我明确确认其他情况。
5. 补充界面主题、主要分区、配色 / 字体、换名对照、设计目的与机制如何影响情绪。灵感来源、为什么好玩、机制决定情绪等内容必须依据我的信息；未知时向我询问或标为待确认。
6. 将草稿放在 docs/cases/_drafts/ 下，不要直接放进正式案例目录。若仓库不存在或无法访问，不要伪造脚本已运行或目录已生成；改为在现有工作区生成清晰标注的投稿草稿，并说明差异。

如果是主题 / 换名方案或完整施工稿，按正式投稿规范生成适当的 Markdown 草稿；不要硬套 HTML 检查器。

### 5. 检查与交付
- 运行当前环境中确实可用的投稿检查；有条件时运行仓库质量检查。逐条记录实际命令与真实结果，不要声称执行过没执行的命令。
- 检查草稿不含真实秘密、个人信息或私有配置；本地检查通过不等于维护者审核通过。
- 输出简短交付摘要：投稿类型、生成 / 修改的文件路径、运行的检查及结果、仍需作者确认的事项。
- 给我下一步操作：推荐把草稿内容贴到仓库 Issue 投稿入口，或在确认规范后自行发起 PR。正式流程见 docs/cases/README.md。

### 6. 权限边界
未经我明确指示，不要提交 Git commit、推送分支、创建 PR / Issue、发布文件或自动修改正式案例索引、CHANGELOG。
不要声称案例已经收录、审核通过或被维护者认可。最终是否收录由仓库维护者人工审核决定。

现在开始盘点工作区。先报告发现的项目结构与投稿类型；如有足够信息，再继续检查和生成草稿。
